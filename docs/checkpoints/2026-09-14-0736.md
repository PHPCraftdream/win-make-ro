# Checkpoint — 2026-09-14 07:36

## Session summary

The user is building `win-make-ro`, a Windows Explorer context-menu extension
that adds **Make read only** / **Remove read only** to files and folders. Work
started from an empty directory and the whole project was written this session,
in Rust with `windows` 0.62.2, targeting edition 2024.

The lock mechanism was chosen deliberately over the NTFS READONLY attribute
alone: it is an explicit deny ACE for `Everyone` carrying exactly
`FILE_WRITE_DATA | FILE_APPEND_DATA | FILE_WRITE_EA | FILE_WRITE_ATTRIBUTES |
DELETE | FILE_DELETE_CHILD`. The user asked several times whether a separate
marker was needed; the conclusion was no — that exact mask *is* the signature,
so nothing extra has to be stored or can be accidentally deleted. Folders get
an inheritable (OI|CI) ACE so Windows propagates the lock across the subtree in
one call, and unlocking a folder removes nested explicit locks during a walk.

The workspace has four crates: `ro-core` (ACL logic), `ro-register` (per-user
`HKCU\Software\Classes` registration), `win-make-ro` (helper executable and
CLI, with a UAC re-launch on ERROR_ACCESS_DENIED), and `ro-shellext` (the COM
DLL implementing `IShellExtInit` + `IContextMenu`). The user imposed structural
rules that are being honoured and checked: one export per file, at most 7
entries per directory, at most 500 lines per file. An icon supplied in
`assets/main_icon.png` was shrunk from 933 KB to 167 KB, converted to
`app.ico`, embedded in both binaries via `embed-resource`, and drawn into the
menu items as a 32-bit DIB.

Two rounds of external code review arrived mid-session and both were verified
and fixed. Round one found five defects (inherited-lock shadowing, walking
through a junction root, NULL DACL destruction, COM unload accounting, argument
quoting). Round two found six more (NULL-DACL heuristic ignoring ACE flags,
lock failing under a locked parent, a half-unlocked file left READONLY,
INHERIT_ONLY treated as a lock, GetCommandString writing through a zero-length
buffer, QueryContextMenu ignoring idCmdLast). Every finding was reproduced
before being fixed, and every regression test was checked counterfactually —
reverting the fix must make the test fail.

Three methodology traps were hit and are worth remembering. First, `icacls`
expands its `(W)` shorthand to `FILE_GENERIC_WRITE` when *parsing* input, so an
ACE built that way has mask 0x130156, not the 0x10156 the lock uses; a test
that looked green was passing for the wrong reason. Second, PowerShell's
`Set-Acl` is unusable on the GitHub runner because `Microsoft.PowerShell.
Security` fails to autoload, so the inherit-only ACE is now assembled directly
with Win32 calls. Third, `cp` on this filesystem preserves mtime, which made a
counterfactual look like a stale-build bug in cargo; it was not.

The repository is published at https://github.com/PHPCraftdream/win-make-ro,
currently **private**. It has dual MIT / Apache-2.0 licensing, README badges,
a GitHub description and ten topics, `.gitattributes`, `rustfmt.toml`, and a CI
workflow on `windows-latest` running fmt, clippy with `-D warnings`, tests and
a release build. CI is green on HEAD (`28e5f79`). 47 tests pass. The working
tree is clean and everything is pushed.

The context menu is currently registered on this machine from `dist\`, so the
extension is live in Explorer. Note that Explorer keeps the DLL loaded, which
blocks overwriting `dist\ro_shellext.dll` until `explorer.exe` restarts.

## Decisions

- Chose an ACL deny ACE over the NTFS READONLY attribute alone: the attribute
  is advisory and any program clears it, while the ACE binds administrators too.
- Chose the exact access mask as the lock's signature over a sidecar marker
  (signature SID ACE, alternate data stream, or extended attribute): the marker
  cannot drift from the protection it identifies, and nothing extra can be lost
  on copy or stripped by a tool.
- Chose Rust over Go and C# for the whole stack: a COM in-process shell
  extension loaded into `explorer.exe` should not drag in a runtime, and one
  language keeps the ACL logic testable in a single place.
- Chose a COM `IContextMenu` handler over static registry verbs: only a handler
  can hide **Remove read only** when the selection is not locked.
- Chose to add the READONLY attribute on locked *files* in addition to the ACE,
  after CI showed that `FILE_DELETE_CHILD` on the parent bypasses a `DELETE`
  deny on the file itself.
- Chose to refuse unlocking an item while a parent's lock still applies, rather
  than strip its ACE and risk leaving the READONLY attribute orphaned.
