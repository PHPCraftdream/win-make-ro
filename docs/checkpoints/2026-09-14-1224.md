## Session summary

The user is building `win-make-ro`, a Windows Explorer context-menu extension
adding **Make read only** / **Remove read only** to files and folders. The
whole project was written in this session, in Rust with `windows` 0.62.2,
edition 2024, MSRV 1.85.

The lock is an explicit deny ACE for `Everyone` carrying exactly
`FILE_WRITE_DATA | FILE_APPEND_DATA | FILE_WRITE_EA | FILE_WRITE_ATTRIBUTES |
DELETE | FILE_DELETE_CHILD`. That exact mask *is* the marker — the user asked
about this repeatedly and the conclusion was that no sidecar marker (signature
SID, ADS, extended attribute) is needed or wanted. Folders get an inheritable
OI|CI ACE so Windows propagates it in one call; the recursive walk adds an
explicit ACE wherever inheritance alone would not hold. Locked files also get
the READONLY attribute, because `FILE_DELETE_CHILD` on the parent otherwise
bypasses a `DELETE` deny.

Four crates: `ro-core` (ACL logic plus the `paths_file` channel), `ro-register`
(per-user HKCU registration), `win-make-ro` (helper exe and CLI with UAC
re-launch), `ro-shellext` (the COM DLL). The user imposed structural rules that
are enforced and checked every round: one export per file, at most 7 entries per
directory, at most 500 lines per file.

The bulk of the session was six consecutive external code reviews, each
delivered as a list of findings. Every finding was reproduced before being
fixed, and every regression test was verified counterfactually — reverting the
fix must make the test fail. Rounds one through five covered ACL semantics
(inherited-lock shadowing, junction roots, NULL DACL, INHERIT_ONLY, the
half-unlocked READONLY state), COM contracts (unload accounting, `idCmdLast`,
zero-length `GetCommandString` buffer, `CMIC_MASK_UNICODE` for both string and
numeric verbs), lossless UTF-16 paths everywhere, MSRV, and the release
workflow (masked exit codes, republished archives changing their SHA-256,
SemVer downgrade guard, Int32 ceiling in the comparator).

The sixth and most recent review (against `970ed0e`) found five more, all fixed

## Decisions

- Chose an ACL deny ACE over the NTFS READONLY attribute alone: the attribute
  is advisory, the ACE binds administrators too. READONLY was later added *in
  addition*, for the `FILE_DELETE_CHILD` bypass only.
- Chose the exact access mask as the lock's signature over any sidecar marker:
  the marker cannot drift from the protection it identifies, and nothing extra
  can be stripped by a tool or lost on copy.
- Chose to refuse a NULL DACL rather than convert it: it switches the access
  check off rather than granting rights, so no ACL reproduces it and no unlock
  could prove a reconstructed one came from a NULL DACL.
- Chose to treat every ACE type that is not a known deny as granting, rather
  than enumerate allow types: an unrecognised ACE cannot be proven harmless and
  the cost of being wrong is a file that is writable while reported locked.
- Chose a UTF-16 file channel (`--paths-from`) over batching for selections too
  large for a command line: batching would multiply UAC prompts and error
  dialogs.
- Chose the packaged native executable as the npm `bin` entry over a JS
  launcher: Node replaces an unpaired surrogate with U+FFFD while building
  `process.argv`, so a JS launcher cannot forward such a name at all.
