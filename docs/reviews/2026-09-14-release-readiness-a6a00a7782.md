**Ревью новых исправлений и готовности win-make-ro к релизу — 2026-09-14**

**Вердикт: к публичному выпуску через описанные npm/Scoop-каналы пока не готов.** Четыре замечания [прошлого ревью](2026-09-14-f5a8170.md) исправлены в проверенных сценариях. Все 75 Rust-тестов проходят в debug и release. При общем обзоре обнаружены два других препятствия: необеспеченная зависимость бинарников от MSVC runtime и удаление пользовательского файла списком командой `status --paths-from`. Проверена рабочая копия на основе `f5a8170094a8796a20e65796bbf6409adc6b9781`: 12 изменённых отслеживаемых файлов и новый `crates/ro-core/src/paths_file/guard.rs`. Исправления ещё не закоммичены. SHA-256 снимка исходников/конфигурации/документации без `docs/reviews/`: `a6a00a7782743e0ad173642aef345172bb12df9b3f867429cb2a8f5aaa9d1005`. Во время проверок содержимое снимка не менялось. В нём 112 файлов, 5 504 строки кода, конфигурации и тестов без Markdown и Cargo.lock.

**P1. Пакеты не обеспечивают необходимый MSVC runtime.**

Места: [release.yml](../../.github/workflows/release.yml#L42), строки 42–44; [Scoop-манифест](../../bucket/win-make-ro.json#L12); [npm-манифест](../../npm/package.json#L34). Это замечание к готовности всего продукта, а не регрессия последних Rust-исправлений.

Проверена таблица импорта собранных release-артефактов:

| Артефакт | Архитектура PE | Внешняя зависимость |
|---|---|---|
| `win-make-ro.exe` | `0x8664`, x86_64 | `VCRUNTIME140.dll` |
| `ro_shellext.dll` | `0x8664`, x86_64 | `VCRUNTIME140.dll` |

Точный шаг `Stage the package` из workflow выполнен на отдельной копии текущего дерева. ZIP содержит только EXE, DLL, README и две лицензии. В npm tarball также нет runtime. Scoop не объявляет соответствующую зависимость; в инструкциях установки отсутствует такой prerequisite. Таким образом, на Windows без подходящего runtime helper не сможет загрузиться до входа в `main`, а DLL — в Explorer. Необходимость обеспечить совместимый runtime для динамически связанных приложений описана у [Microsoft](https://learn.microsoft.com/en-us/cpp/windows/deploying-visual-cpp-application-by-using-the-vcpp-redistributable-package?view=msvc-170).

На машине ревью `VCRUNTIME140.dll` уже установлен, поэтому успешные локальные тесты и запуск из npm эту проблему не исключают. Отдельный запуск на чистой Windows без runtime не выполнялся; вывод о такой машине основан на импортах артефактов и контракте загрузки зависимостей.

До выпуска нужно выбрать и реализовать способ доставки зависимости: объявить и обеспечить установку совместимого redistributable либо собрать подходящие артефакты со статическим CRT и повторно проверить импорты и COM-сценарии. Возможность выбора CRT для MSVC описана в [Rust Reference](https://doc.rust-lang.org/reference/linkage.html#static-and-dynamic-c-runtimes). При выборе установщика runtime нужно согласовать это с обещанием установки без прав администратора. Проверка готового пакета должна проходить на машине без средств разработки и случайно установленных зависимостей.

**P2. `status --paths-from` без предупреждения удаляет пользовательский входной файл.**

Места: [run.rs](../../crates/win-make-ro/src/cli/run.rs#L8), строки 8–9; новая публичная справка [usage.rs](../../crates/win-make-ro/src/cli/usage.rs#L11), строки 11–13. Автоудаление существовало раньше как часть IPC; последние изменения показывают этот параметр пользователю в справке, не объясняя передачу владения файлом и его удаление.

`Args::parse` принимает произвольный файл по пути пользователя. После `dispatch` функция `run` безусловно удаляет его, не различая созданный программой временный IPC-файл и сохранённый пользователем список. Это происходит и для команды чтения `status`, и при ошибке обращения к целям.

Воспроизведение выполнено release-бинарником на собственных fixtures. Файл списка содержал одно относительное имя, закодированное UTF-16LE без BOM:

| Команда / содержимое списка | Код | Список после команды |
|---|---:|---|
| `status --paths-from existing.paths`, существующий `target.txt` | 0 | Удалён |
| `status --paths-from missing.paths`, отсутствующий `missing.txt` | 1 | Удалён |
| Смешанный ввод `lock --paths-from mixed.paths extra.txt` | 2 | Сохранён; новые проверки корректно отвергли ввод до выполнения |

Обычный файл цели при `status` остался неизменным; потерян именно файл списка. Повторное использование такого списка невозможно. Справка описывает получение выборки из файла, но не предупреждает о его уничтожении.

Исправление: развести пользовательские списки и одноразовые IPC-файлы. По умолчанию сохранять пользовательский файл; автоудаление явно запрашивать только для файла, переданного во владение helper внутренним протоколом. Также описать формат списка. Нужны проверки сохранения входных байтов при успешном `status` и при ошибке, вместе с существующими проверками очистки служебных файлов.

**Результат ревью последних четырёх исправлений**

| Прежнее замечание | Изменение | Проверка и решение |
|---|---|---|
| P2-1: panic на DACL предельного размера | `AclBuilder::new` возвращает `Result`, считает занятые ACE байты, проверяет предел 65 532 и передаёт отказ вызывающему коду | Принято. Реальная большая DACL даёт код 1; файл остаётся доступным для записи, следующая цель блокируется. Тест проходит в обоих профилях. Конструктор вызывается до изменения READONLY. |
| P2-2: ложный `LockedByParent` при другом написании пути | Отложенные цели с единственным отказом из-за родителя повторяются после остальных; завершение обеспечено сокращением списка pending | Принято. Регрессии регистра и verbatim-префикса проходят. Дополнительная проверка с отсутствующей независимой целью сохранила настоящую ошибку и убрала ложную; без выбранного родителя отказ сохраняется. |
| P2-3: потеря целей при смешивании `--paths-from` | Смешанные и повторные источники отклоняются, добавлено обратное преобразование корректного списка | Принято. Смешанный ввод даёт код 2 до применения ACL. Два корректных пути сохраняются после `parse → to_argv → parse`. |

Очистка частично записанного списка после ошибки `write_all` также исправлена: handle сначала закрывается, затем выполняется удаление. Ошибка записи на полный диск специально не воспроизводилась. Новых подтверждённых дефектов в четырёх механизмах исправления не найдено; P2 выше относится к другому контракту — владению пользовательским входным файлом.
