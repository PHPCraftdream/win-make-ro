**P1. Относительный `--to` сохраняется в COM-регистрации как относительный путь DLL.**

Место: [reinstall/run.rs](../../crates/win-make-ro/src/reinstall/run.rs#L49), строки 49–54. Введено в `672ee2e`; именно такой вызов показан в [README](../../README.md#L170).

Ветка `Some(dir)` создаёт и заполняет каталог, затем без преобразования сохраняет `dir.to_path_buf()`. `ro_register::install` передаёт `to.join("ro_shellext.dll")` в `REG_SZ` без приведения к абсолютному пути. При `--to dist` запись получается `dist\ro_shellext.dll`, а не полный путь к размещённой DLL.

Воспроизведение использовало настоящий `reinstall/run.rs`, `swap`, `sweep` и настоящий `ro_register::install_under` на отдельном registry key. Глобальная регистрация и перезапуск Explorer были заменены безопасными адаптерами. После `reinstall(Some("relative"))` прочитано:

```text
stored="relative\ro_shellext.dll", absolute=false, copied=true
same registry value resolves from another cwd: false
```

Дополнительно проверен загрузчик Windows с настоящей release-DLL в собственном процессе:

| Путь и рабочий каталог процесса | Результат LoadLibraryW |
|---|---|
| Относительный путь, каталог установки | Успех |
| Тот же относительный путь, другой каталог | Ошибка 126, модуль не найден |
| Абсолютный путь, другой каталог | Успех |

Регистрация становится зависимой от рабочего каталога будущего COM-хоста. Установка может выглядеть рабочей сразу после команды, но не находиться при другом запуске Explorer или после входа в систему. По контракту [LoadLibraryW](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-loadlibraryw) относительный путь участвует в поиске DLL; каталог процесса, выполнявшего регистрацию, в `REG_SZ` не сохраняется.

Исправление: один раз привести `--to` к абсолютному `PathBuf` до файловых операций и использовать его для копирования, регистрации, cleanup и Summary. `std::path::absolute` сохраняет Windows-путь без преобразования через lossy String и не требует раскрывать alias `current` в физический версионный каталог. Добавить проверку относительного `--to`, значения registry key и последующей загрузки из другого cwd.

**P2-1. Откат не удаляет новый файл, если до операции этого файла не существовало.**

Место: [swap.rs](../../crates/win-make-ro/src/reinstall/swap.rs#L64), строки 64–66; откат — строки 85–100. Новая регрессия учёта выполненных действий в `672ee2e`.

В `done` попадают только записи, у которых есть `aside`. Если EXE отсутствовал в адресате, его новая копия успешно устанавливается, но не записывается в журнал отката. При последующем отказе замены DLL `undo` не знает о созданном EXE.

Реальное файловое воспроизведение: источник содержит обе новые копии; адресат содержит только старую `ro_shellext.dll`, открытую с `share_mode(0)`. `swap` получает Win32 error 32 при замене DLL, но после возврата ошибки в адресате остаются новый `win-make-ro.exe` и старая DLL. Такая неполная установка могла остаться после прежнего сбоя; отсутствие одного из файлов в адресате не запрещено API.

```text
partial rollback: os error 32
new EXE left=true
DLL remains old=true
```

Исправление: учитывать каждое успешно поставленное конечное имя, включая записи без прежнего файла: `(final_name, Option<backup>)`. При откате новый файл удаляется, а старая копия восстанавливается только при её наличии. Проверять восстановление исходного набора файлов для полностью заполненного, пустого и частично заполненного адресата. Также учитывать ошибку немедленного восстановления текущего `aside` на строке 60: сейчас она по-прежнему игнорируется.

**P2-2. Предварительная очистка может уничтожить последнюю копию для восстановления до начала нового обмена.**

Место: [reinstall/run.rs](../../crates/win-make-ro/src/reinstall/run.rs#L44), строки 44–48; распознавание и удаление — [sweep.rs](../../crates/win-make-ro/src/reinstall/sweep.rs#L32).

`sweep(dir, &[])` выполняется перед `swap`. Имя `.superseded-<pid>-<nanos>.old` доказывает выбранную схему именования, но не подтверждает, что прежний обмен и откат закончились успешно. Если возврат старой DLL на её основное имя не удался, либо операция была прервана, такой файл может быть единственной исправной копией, нужной для восстановления.

В адресате создана резервная DLL с допустимым именем, основной DLL нет. Исходная DLL следующей попытки открыта без sharing: `is_file()` успешно подтверждает её наличие, но настоящее копирование Windows отказывает с error 32. Результат настоящего `run`/`swap`/`sweep`:

```text
real source sharing error=true
last backup survived=false
result=error 32
```

Таким образом, новая установка не произошла, а сохранённая старая копия уже удалена. Сначала этот порядок был проверен с подменённым отказом staging, затем подтверждён настоящей ошибкой файловой системы; основной вывод не зависит от искусственного отказа.

Исправление: не удалять recovery-копии до успешной подготовки и фиксации нового состояния. Для предыдущих попыток различать завершённый обмен, незавершённую операцию и неудачный откат, сохраняя журнал или иной проверяемый статус операции. Минимум — сохранять backup при неполной действующей паре и не выполнять общую очистку перед потенциально неуспешным staging. Проверять повтор после неудачного отката вместе с ещё одной ошибкой подготовки.

**Дополнительные замечания и ограничения**

- В [cli/run.rs](../../crates/win-make-ro/src/cli/run.rs#L57) общий текст для `Restart::Failed` утверждает, что Explorer продолжает выполнять старую копию. Это неверно для отказа `start()` после успешного завершения старого процесса: [explorer.rs](../../crates/win-make-ro/src/reinstall/explorer.rs#L120) сам сообщает, что старый Explorer уже закрыт. Следует сохранять фазу отказа либо убрать неподтверждённое утверждение из общего сообщения.
- Смена установщиков остаётся ограничением удаления. На отдельном registry key проверена последовательность «регистрация A → регистрация B → uninstall_under»: активная регистрация B удаляется. Это соответствует глобальной семантике текущего `uninstall`, но автоматический Scoop hook не проверяет принадлежность регистрации удаляемому пакету. Для поддержки смешивания каналов нужна такая проверка; иначе ограничение следует явно описать.
- README продолжает объяснять npm update через перезапись DLL. В предыдущем безопасном опыте с npm 11.13 пакет обновился через переименование старого каталога, а блокировка DLL дала предупреждение cleanup. Это не новая проверка в данном ходе; прежнее уточнение механизма всё ещё актуально.
- Отсутствие прежней регистрации не измеряет отсутствие загруженной DLL. `Restart::NotRequested.describe()` исправлен, но README и первый комментарий этого enum всё ещё делают более сильное утверждение.
- Фраза README «everything is covered» не подтверждается тестами: относительный адресат, неполная старая пара и recovery-состояние отсутствуют в штатном наборе. Число тестов верно, полнота контрактов из него не следует.
- Настоящие UAC и закрытие/повторное открытие пользовательского Explorer не проверялись. Windows 11 отдельно не проверялась. Определение наличия shell и чтение собственного токена — проверки другого уровня и их не заменяют.
