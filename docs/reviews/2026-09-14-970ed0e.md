Полный обзор репозитория win-make-ro, состояние `970ed0e`.

Обзор выполнен заново по текущим исходникам, тестам, манифестам и workflow. Последнее изменение SemVer проверено отдельно. Производственные исходники не изменялись. Отчёт сохранён в `docs/reviews/`; локальные артефакты воспроизведений находятся в игнорируемой Git папке `target/review-970ed0e/` и не входят в репозиторий.

Общий результат: два подтверждённых дефекта P1 в защите файлов и передаче имён, три замечания P2 в обработке выбора и инструкции установки. Штатные тесты проходят, но не охватывают найденные сценарии.

Архитектура и границы ответственности:

| Компонент | Назначение | Результат обзора |
|---|---|---|
| `ro-core` | Читает и перестраивает DACL, добавляет deny-ACE, обходит дерево | Итеративный обход, сохранение чужих ACE, обработка NULL DACL и наследования понятны; распознавание разрешающих ACE неполно — см. P1-1. |
| `ro-register` | Персональная регистрация COM в HKCU | UTF-16 сохраняется при записи и чтении. Тесты работают с отдельными ключами. Новых подтверждённых дефектов в текущих путях регистрации не найдено. |
| `win-make-ro` | CLI, отчёты, запуск через UAC | Нативные пути и quoting сохраняют UTF-16. Есть зависимость результата от порядка пересекающихся целей — P2-2. |
| `ro-shellext` | Получает выделение, формирует меню и запускает helper | Проверены COM-интерфейсы, числовые/строковые verbs, счётчики и bitmap. Передача большого выделения ограничена командной строкой — P2-1. |
| `npm` | Упаковывает EXE/DLL, предоставляет launcher и postinstall | Удаление регистрации документировано. JS launcher теряет непарные суррогаты — P1-2. |
| Scoop и release workflow | Архивы, checksum, публикация и обновление манифеста | Планирование assets, проверка кодов возврата и защита от отката рассмотрены. Текущие тесты скриптов проходят; реальная публикация не выполнялась. |

Поток выполнения: Explorer передаёт выделение в `ro-shellext`; DLL запускает отдельный `win-make-ro.exe`, который вызывает `ro-core`. Регистрация вынесена в `ro-register`. npm добавляет перед EXE ещё один процесс Node.js — именно на этой границе обнаружена потеря имени.

В отслеживаемых исходниках, тестах и конфигурациях перечисленных компонентов примерно 4,6 тысячи строк. Зафиксированы `windows/windows-core 0.62.2`, `windows-registry 0.6.1`, `embed-resource 3.0.11`, `tempfile 3.27.0`. Это фиксация разрешённых зависимостей, а не отдельная проверка базы уязвимостей.

Подтверждённые замечания:

1. **P1-1 — условный allow-ACE обходит блокировку потомка.**

   Место: [ace_ref.rs](../../crates/ro-core/src/win/acl/ace_ref.rs), строки 36–37; [lock_shadowed.rs](../../crates/ro-core/src/win/acl/state/lock_shadowed.rs), строка 17.

   `is_allow()` узнаёт только обычный `ACCESS_ALLOWED_ACE_TYPE`. Условный `ACCESS_ALLOWED_CALLBACK_ACE_TYPE` (SDDL `XA`, тип 9) может разрешать запись перед унаследованным deny, но `lock_shadowed()` его пропускает. Потомок остаётся без собственного deny.

   Воспроизведение: у файла внутри обычной папки установлен `D:(XA;;FA;;;WD;(Member_of {SID(S-1-1-0)}))`. После `lock --no-elevate -- <папка>` получены exit 0 и статус файла `inherited`; `WriteAllText` успешно изменяет файл. Условный ACE сохранился типом 9 с маской `0x1F01FF`. Контрольные обычные allow-ACE блокировались.

   Исправление: учитывать все применимые разновидности разрешающих ACE, включая условные, либо консервативно ставить собственный deny там, где нельзя доказать достаточность наследования. Проверять реальную запись, а не только наличие маркера.

   Семантика условных ACE: [Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-descriptor-definition-language-for-conditional-aces-).

2. **P1-2 — npm launcher меняет адресата операции.**

   Место: [win-make-ro.js](../../npm/bin/win-make-ro.js), строка 11.

   Созданы два разных NTFS-файла: имя первого содержит UTF-16 unit U+D800, имя второго — U+FFFD. Запуск JS launcher с первым именем завершился кодом 0, оставил первый файл unlocked и заблокировал второй. Потеря происходит уже при формировании `process.argv` в проверенном Node.js 24.12.0: в нём нет U+D800 и есть U+FFFD.

   Исправление: предоставить точку входа, которая не пропускает Windows-пути через Node.js. В изолированном прототипе `bin` указывает прямо на `vendor/win-make-ro.exe`; созданный npm `.cmd`-shim обработал то же имя правильно. Локальный прототип находится в `target/review-970ed0e/package-native-prototype/`, исходный `npm/package.json` не изменён. Для маршрутов через сам `npx` ограничения Node нужно учитывать отдельно.

3. **P2-1 — большое выделение не доходит до helper.**

   Место: [launch.rs](../../crates/ro-shellext/src/menu/launch.rs), строки 16–22.

   Весь список передаётся одной командной строкой. Воспроизведено на 180 существующих файлах с обычными именами и путями примерно по 180 символов: вместе с разделителями, именем EXE и опциями строка превышает лимит; меню предложило команды, а `InvokeCommand` вернул `0x80004005`. Файлы остались unlocked. Лимит `CreateProcessW` — 32767 символов с завершающим NUL.

   Исправление: передавать список через отдельный канал/файл либо разбивать запуск на партии с учётом длины аргументов после quoting и корректно объединять результат.

   Лимит API: [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw).

4. **P2-2 — ложный отказ при выборе потомка раньше родителя.**

   Место: [apply.rs](../../crates/win-make-ro/src/ops/apply.rs), строки 10–18.

   После блокировки папки команда `unlock --no-elevate -- <child> <parent>` сначала сохраняет `LockedByParent`, затем успешно разблокирует родителя и файл, но возвращает 1 со старым сообщением об ошибке. Для того же набора целей в порядке `<parent> <child>` возвращается 0. Нужно учитывать отношения между целями и обрабатывать предков раньше потомков, сохраняя корректную обработку действительно недоступных веток.

5. **P2-3 — инструкция ручной установки ссылается на отсутствующие файлы.**

   Место: [README.md](../../README.md), строки 114–115.

   `dist/install.cmd` и `dist/uninstall.cmd` отсутствуют среди отслеживаемых файлов. Приведённые команды сборки их не создают, release workflow их не упаковывает. Из чистого checkout эти команды не выполнятся. В инструкции следует вызывать существующий `dist/win-make-ro.exe install` и `uninstall` либо поставлять сами скрипты.

Наблюдения о тестовом слое и ограничениях модели:

- Штатные проверки в основном используют обычные ACE и нативный CLI. Они не включают найденные условный allow-ACE, npm launcher с непарным суррогатом, предел командной строки и пересекающиеся цели.
- `tests/common::Dll` держит `HMODULE` без `Drop`. Обычные COM-тесты не освобождают эти ссылки. Поэтому ручные пары LoadLibrary/FreeLibrary в GDI-тесте не гарантируют реальную выгрузку DLL, если раньше в том же процессе прошёл другой тест. Стоит сделать владение библиотекой явным и отдельно проверять загрузку/выгрузку.
- Некоторые проверки ACL зависят от английских строк `icacls`, например `Everyone:(F)`. Для проверки SID, масок и наследования надёжнее читать структуру ACL непосредственно.
- DACL не отзывает права у уже открытого дескриптора. Проверено: lock вернул 0, новый writable handle получить нельзя, но запись через ранее открытый handle прошла. Это существенная граница механизма, которую следует явно описать пользователю.
- Успешный unlock очищает READONLY; исходное значение этого атрибута не сохраняется. Операция не является побитовым восстановлением всей исходной метаинформации файла.

В рамках этого обзора не запускались публикация в GitHub/npm, установка в живой Explorer и реальное подтверждение UAC. Проверки COM выполнялись в тестовых процессах, регистрационные тесты — на отдельных ключах, проверки файлов — на собственных временных объектах. Их блокировки сняты после воспроизведений.

Практический порядок дальнейшей работы: сначала P1-1 и P1-2 с регрессиями на реальные операции, затем передача больших выделений и порядок целей, затем инструкция установки и усиление тестов жизненного цикла.
