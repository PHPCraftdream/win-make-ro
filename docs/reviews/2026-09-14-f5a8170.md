**Замечания**

**P2-1. Допустимая DACL большого размера аварийно завершает helper и прерывает остальные цели.**

Место: [builder.rs](../../crates/ro-core/src/win/acl/builder.rs#L35), строки 35–39. Дефект существовал до последних исправлений.

`AclBuilder::new` прибавляет размер нового ACE к `AclSize` и считает, что `InitializeAcl` обязательно выполнится. Размер исходной DACL задаётся файловой системой, поэтому это не инвариант программы: новая ACL может выйти за допустимый размер. В структуре ACL размер хранится в `WORD`; Microsoft указывает предел 64 КБ и допускает ошибку `InitializeAcl`. [Структура ACL](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-acl), [InitializeAcl](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-initializeacl).

Воспроизведение на собственном файле: установить защищённую DACL из `D:P(A;;FA;;;WD)` и 3 275 записей `(A;;FR;;;S-1-5-N)`, где N принимает разные значения от 10000 до 13274. `SetNamedSecurityInfoW` возвращает 0; повторное чтение подтверждает `AclSize=65528`, `AceCount=3276`. Разные SID существенны: одинаковые ACE Windows может объединить, и такой контроль не проверяет границу размера.

Затем вызвать `lock --no-elevate -- large-acl.txt z-after-large-acl.txt`. В debug и release helper завершился с кодом **101**, сообщением `invariant: fresh buffer of valid size` и HRESULT `0x80070057` на строке 39. Во втором файле проверено состояние `unlocked`: обработка до него не дошла. Это нарушает контракт накопления ошибок без остановки остальных целей.

Исправление: вычислять требуемое место с учётом ограничения ACL, возвращать `Result` из конструктора и передавать отказ в `Report`. Если в исходной ACL есть свободное место, учитывать фактически занятые байты вместо безусловного увеличения всей ёмкости. Регрессия должна проверять обычный код ошибки 1, отсутствие изменения проблемного файла и обработку следующей независимой цели.

**P2-2. Сортировка путей не гарантирует обработку родителя раньше ребёнка на Windows.**

Место: [apply.rs](../../crates/win-make-ro/src/ops/apply.rs#L34), строки 34–37. Неполное исправление прежнего P2-2, добавленное в `8ef6f86`.

`std::path::absolute` и обычный `PathBuf::sort` не устанавливают тождество разных написаний Windows-пути. Приведение к абсолютному пути не обращается к файловой системе; verbatim-пути возвращаются без такого преобразования. [Документация Rust](https://doc.rust-lang.org/std/path/fn.absolute.html).

На обычном каталоге без чувствительности к регистру создана пара `parent/child.txt`. После блокировки родителя получены следующие результаты; в каждом случае конечный статус обоих объектов — `unlocked`:

| Переданные пути | Код unlock | stderr |
|---|---:|---|
| Обычные пути ребёнка и родителя с одинаковым написанием компонентов | 0 | Пусто |
| В пути ребёнка компонент `PARENT`, в пути родителя `parent` | 1 | `locked by a parent folder, unlock it instead` |
| Путь ребёнка с префиксом `\\?\`, путь родителя без него | 1 | То же сообщение |
| Обычный путь ребёнка, путь родителя с префиксом `\\?\` | 0 | Пусто |

При двух проблемных вариантах сортировка ставит ребёнка первым, сохраняет промежуточный `LockedByParent`, а затем успешно разблокирует всё через родителя. Автоматизация и GUI получают ложный результат о неудаче.

Исправление: определять порядок по отношению предок/потомок с учётом Windows-путей либо повторно обрабатывать зависимые от родителя отказы после остальных целей. Простого перевода строк в нижний регистр недостаточно для всех допустимых Windows-каталогов. Добавить реальные файловые проверки разных регистров и verbatim/обычного написания, сохранив ошибки действительно недоступных объектов.

**P2-3. Повторный запуск теряет дополнительные цели рядом с `--paths-from`.**

Место: [args.rs](../../crates/win-make-ro/src/cli/args.rs#L77), строки 77–80; приём нескольких источников — строки 32–38 и 51. Новая регрессия файлового канала из `8ef6f86`.

Парсер принимает список из файла вместе с обычными позиционными путями и объединяет их в `args.paths`. Он также принимает несколько `--paths-from`, сохраняя в `paths_file` только последнее имя. Однако `to_argv` при наличии файла возвращает только его и перестаёт кодировать остальную выборку. Именно этот метод вызывает [elevate.rs](../../crates/win-make-ro/src/ops/elevate.rs#L48).

Проверка выполнена на подключённых без копирования текущих модулях `Args` и `Command`. Файл списка содержал `listed.txt`, входные аргументы — `lock --paths-from LIST extra.txt`:

```text
original paths: ["listed.txt", "extra.txt"]
forwarded paths: ["listed.txt"]
```

Если для дополнительной цели требуется повышение прав, дочерний процесс её уже не получит. Из кода следует возможность возврата успеха после обработки только оставшейся части выборки. Потеря аргумента воспроизведена непосредственно; реальный диалог UAC и этот конечный код через UAC не запускались.

Исправление: либо отклонять смешанные и повторные источники при разборе, либо создавать для повторного запуска полный снимок `args.paths`. Нужны проверки сохранения всех целей после `parse → to_argv → parse` для смешанного ввода и двух файлов списков.

**P3-1. Отмена UAC оставляет файл списка, созданный внутри `elevate`.**

Место: [elevate.rs](../../crates/win-make-ro/src/ops/elevate.rs#L66), строки 66–72; создание файла — строки 31–35, очистка — строки 83–84. Новое замечание по обработке ошибок в `8ef6f86`, подтверждённое анализом управления и владения, без интерактивного воспроизведения UAC.

Условие: исходный запуск передал пути прямо в командной строке, они ещё помещаются в лимит Windows, но превышают внутренний бюджет 30 000 единиц UTF-16. При необходимости повышения прав `elevate` создаёт файл и записывает его имя только в локальную копию `child`. Если `ShellExecuteExW` вернёт отказ, включая отмену пользователем, ранний `return` обходит очистку. Внешний [run.rs](../../crates/win-make-ro/src/cli/run.rs#L8) проверяет исходный `args.paths_file`, который в этом сценарии равен `None`.

Результат — оставшийся в TEMP файл с перечнем путей; повторные отмены накапливают такие файлы. Для списка, уже переданного из Explorer, внешний `run` выполняет очистку, поэтому замечание относится именно к созданию файла внутри `elevate`.

Исправление: владеть вновь созданным файлом через guard, покрывающий все выходы. Проверять отказ запуска и отмену UAC через подменяемую границу запуска процесса. Сходный ранний выход при неудачном `write_all` в [write.rs](../../crates/ro-core/src/paths_file/write.rs#L27) также стоит включить в проверку очистки незавершённого файла.

**Оставшиеся ограничения и качество тестов**

- Предельный размер DACL должен проверяться вместе с продолжением обработки второй цели, иначе тест зафиксирует только отказ первого файла и пропустит аварийное завершение всей команды.
- Тест сортировки использует одно написание пути; он не проверяет тождественные Windows-пути с разным регистром и префиксом. Проверка `Args` на обратное преобразование пока не включает `--paths-from`.
- npm-тест нового `bin` проверяет декларацию манифеста. Для защиты от регрессии запуска нужен хотя бы один тест реального установленного shim, подобный выполненному в этом обзоре.
- Очистка временных файлов при ошибке записи/запуска и отмене UAC не покрыта штатными проверками. Передача списка через изменяемый файл также не доказывает неизменность снимка между первичным запуском и чтением ребёнком; конкурентная подмена в этом обзоре не воспроизводилась.
- Блокировка не гарантирует неподвижность самого корневого каталога: его переименование через права внешнего родителя удалось и в release. Дочерний файл после переименования сохранил `inherited`. Это ограничение области защиты имён, а не найденный обход запрета записи внутрь заблокированной папки. Имеет смысл явно добавить этот пример в README.
- Сохранение ранее открытых пишущих дескрипторов теперь описано в README. Восстановление первоначального READONLY-бита после lock/unlock не реализовано: unlock снимает его. Полный побитовый возврат метаданных не следует считать гарантией этой реализации.
- Не выполнялись публикация GitHub/npm, установка через Scoop, регистрация тестовой сборки в живом Explorer и подтверждение/отмена настоящего UAC. Windows 11 Explorer отдельно не проверялся.
