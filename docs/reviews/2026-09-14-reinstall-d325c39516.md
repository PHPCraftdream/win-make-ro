На начало проверки они находились в рабочем дереве; к завершению те же исходники вошли в `723951233fe704d6809d9d80cc16968cf9b68326`. Основной вывод: решение о перезапуске действительно лучше принимать в Rust, где доступна прежняя регистрация. Но эта регистрация не должна автоматически определять, куда npm копирует файлы. Одного пояснения в README недостаточно. Автоматическое обновление в текущем виде требует исправления адресата и очистки; гарантии настоящего перезапуска Explorer ещё не подтверждены.

**P1. Автоматический npm hook может перезаписать установку другого менеджера.**

Место: [reinstall/run.rs](../../crates/win-make-ro/src/reinstall/run.rs#L46), строки 46–57, и `destination`, строки 77–83; вызов из [postinstall.js](../../npm/scripts/postinstall.js#L36).

Адресат берётся из старого `InprocServer32`, если его родительский каталог существует. При отличии от каталога выполняемого EXE туда копируется новая пара бинарников, и регистрация остаётся на этом адресате. Код не различает ручную установку, npm и Scoop.

В воспроизведении настоящий Rust-код `run`, `swap` и `sweep` получил через подмену регистрации путь `scoop/apps/win-make-ro/old-version/ro_shellext.dll`. Источник был отдельным каталогом. Результат: старые файлы в условном Scoop-каталоге заменены, регистрация осталась там, запрошен перезапуск. Реальные Scoop/реестр/Explorer не изменялись; копирование проверено на собственных файлах с различимым содержимым.

Следовательно, риск существует не только при ручном запуске Scoop-пользователем: обычный npm `postinstall` вызывает тот же `reinstall`. При прежней регистрации Scoop или ручной установки обновление npm может записать бинарники в их каталог вместо активации npm-копии. Если регистрация указывает на конкретный старый версионный каталог, последующая его очистка оставит висячую регистрацию.

Уточнение к исходному отчёту: нельзя утверждать, что любой ручной `reinstall` после обычного Scoop update обязательно пишет в старую версию. Scoop использует alias `current`, а имеющийся `post_install` вызывает `install` для актуального `$dir`. Проблемный сценарий требует расхождения фактического источника и зарегистрированного адресата. Механизм `current` описан в [официальной документации Scoop](https://github.com/ScoopInstaller/Scoop/wiki/The-%27Current%27-Version-Alias), переменные hook — в [документации скриптов установки](https://github.com/ScoopInstaller/Scoop/wiki/Pre--and-Post-install-scripts).

Исправление: для пакетных менеджеров выбирать каталог текущего пакета явно; старую регистрацию использовать только как сведения о прежней установке и повод запросить restart. Подменять файлы по старому адресу только по явно заданному пользователем адресу.

**P2. Очистка удаляет ручные резервные копии.**

Место: [sweep.rs](../../crates/win-make-ro/src/reinstall/sweep.rs#L31), строки 31–33. Очистка вызывается уже в начале `reinstall`, строка 52.

`superseded` проверяет лишь префикс имени бинарника, следующую точку и суффикс `.old`. Он не проверяет формат PID/timestamp и не доказывает, что файл создан `swap`.

Реальный `sweep` на собственном fixture удалил `ro_shellext.dll.manual-backup.old`, содержащий `USER-BACKUP`, и вернул пустой список ошибок. Имя `ro_shellext.dll.old` также удовлетворяет этому предикату. Существующий тест защищает `notes.old`, но не резервные копии с именем самого бинарника.

Исправление: `swap` должен возвращать перечень созданных им backup-файлов, а очистка — удалять этот перечень. Для восстановления после прерванной операции нужен сохранённый список/журнал либо отдельный каталог служебных backup-операций. Проверка точного формата имени полезна как дополнительный фильтр, но сама по себе не является доказательством владения файлом. Добавить проверки сохранения `.manual-backup.old` и `.dll.old`.

**P2. Ошибка обнаружения Explorer может превратиться в сообщение об успешном перезапуске.**

Место: [explorer.rs](../../crates/win-make-ro/src/reinstall/explorer.rs#L44), строки 44–57 и 26–39. Подтверждено анализом кода; соответствующие сбои Win32 на живом рабочем столе не вызывались.

`shell()` возвращает `None` как при отсутствии tray window, так и при отказе `OpenProcess`. Затем `restart()` без запроса завершения найденного старого процесса вызывает `start()`. Если создание процесса удалось, наружу возвращается успех; `reinstall` возвращает `restarted=true`, хотя прежний процесс не был остановлен и его DLL может оставаться загруженной. Отказ `OpenProcess` является ошибкой получения handle, а не признаком отсутствия процесса. [Контракт OpenProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-openprocess).

Исправление: `shell() -> Result<Option<ShellHandle>, Error>`, с отдельными исходами «shell не найден» и «не удалось открыть процесс». На ошибке обнаружения не переходить к успешному `start`. Handle должен иметь RAII-владельца: сейчас отказ `PostMessageW` через ранний `?` также обходит `CloseHandle`.

Сходная ошибка есть в [elevated.rs](../../crates/win-make-ro/src/reinstall/elevated.rs#L13): отказ чтения токена превращается в `false`. Для защиты от запуска elevated-Explorer отсутствие ответа нельзя считать доказательством обычного токена. Нужен `Result<bool, Error>`; при ошибке проверки перезапуск не выполняется.

**Что в отчёте требует уточнения**

Поведенческий тест npm возможен без изменения пользовательского рабочего стола. Подготовлена и выполнена локальная проверка `target/review-reinstall-d325c39516/postinstall-probe.cjs`: она исполняет настоящие `paths.js` и `postinstall.js` через `node:vm`, подставляет ответы `spawnSync`, `existsSync`, платформу, env и console. Реальный `child_process` в тестируемый код не передаётся. API отдельного JS-контекста описан в [документации Node.js](https://nodejs.org/api/vm.html#vmruninnewcontextcode-contextobject-options).

Проверены девять сценариев: успешный reinstall; fallback после кода 1; отказ обеих команд; ошибка spawn; завершение ребёнка без exit code; локальная установка; `WIN_MAKE_RO_SKIP_REGISTER=1`; отсутствие EXE; другая платформа. Проверяются последовательность вызовов и сообщения. Перестановка команд в памяти обнаруживается отрицательным контролем. Скрипт не запускает настоящий EXE, не меняет реестр и не отправляет сообщения Explorer. Это проверка поведения, а не поиск строки в исходнике.

В Rust аналогично можно подменять только границы ОС. Для этого обзора исходные `run.rs`, `swap.rs`, `sweep.rs` подключены без копирования в `reinstall-probe.rs`; подменены реестр, определение elevated-токена и `explorer::restart`. Так проверены планирование и реальные файловые последствия. Реальный перезапуск такая проверка, разумеется, не подтверждает.

Утверждение об обновлении npm через простое перезаписывание загруженной DLL не подтвердилось для установленного npm 11.13.0. В отдельном опыте собственный процесс ревью загрузил настоящую DLL через `LoadLibraryExW`, а npm обновил отдельный тестовый пакет с 1.0.0 до 2.0.0. Hook тестового пакета только писал marker и не запускал `reinstall`.

```text
npm exit: 0
installed version: 2.0.0
postinstall marker: 2.0.0
old package: moved into .review-lock-fixture-...
cleanup: EPERM while its DLL was still mapped
```

Таким образом, npm смог поставить новую копию и выполнить postinstall, а не смог удалить старую переименованную копию до освобождения mapping. Это подтверждает пользу сигнала «была регистрация», даже когда `reinstall` сам ничего не копирует. Эксперимент не доказывает успешность любого npm update при любых блокировках; README стоит описывать проверенный механизм и различать отказ установки и предупреждение cleanup.

Fallback сейчас срабатывает на любой неуспех reinstall, а не только на elevated shell. В Rust-проверке ошибка restart возникала уже после копирования и записи регистрации; последующий `install` переключал регистрацию на источник, оставляя ранее изменённый каталог. Такой fallback нельзя считать откатом. После введения явного адресата лучше обрабатывать пропуск restart из-за elevated-токена внутри Rust, а реальные ошибки фаз возвращать с их состоянием.

Фраза `nothing was loaded to replace` сильнее доступного факта. Отсутствие записи в реестре не доказывает отсутствие ранее загруженного DLL, например после unregister. Без отдельной проверки mapping корректнее печатать `no previous registration; Explorer restart not requested`. `was_registered` — практический сигнал политики перезапуска, а не измерение загруженных модулей.

**Рекомендуемый контракт исправления**

Ниже предлагаемый интерфейс; этих новых флагов в проверенной реализации ещё нет.

| Вызов | Адресат | Файловая операция | Перезапуск |
|---|---|---|---|
| `reinstall --here` | Каталог выполняемого EXE | Проверить пару бинарников и зарегистрировать её; чужие каталоги не трогать | Решение по прежней регистрации и разрешённости restart |
| `reinstall --to <dir>` | Явный адрес пользователя | Подготовить/подменить пару в указанном каталоге с учётом rollback | После успешной регистрации, с отдельным результатом restart |
| `install` | Каталог выполняемого EXE | Только регистрация | Не запрашивать |

Для новой, ещё не выпущенной команды рекомендую сделать голый `reinstall` синонимом `--here`, а прежнее поведение ручного копирования перенести в `--to`. Например, обновление ручной установки станет `target\release\win-make-ro.exe reinstall --to dist`. Тогда вызов через любой shim не начинает молча переписывать чужую установку.

В npm передавать полный argv `['reinstall', '--here']`. Если пока сохраняется fallback `install`, константа должна описывать действия вместе с argv, а проверка — полную последовательность аргументов. При замене строк на массивы также нужно изменить `run` и разбор выбранного действия: прежний `switch` по строке больше не подходит.

Для Scoop имеющийся `install` можно сохранить: это уже регистрация текущего `$dir`. Если нужен автоматический restart и для Scoop, hook должен явно вызывать свой EXE с `reinstall --here`. Сохранять сырой путь `current` как адрес регистрации допустимо; canonicalize нужен для сравнения, но не должен без необходимости превращать стабильный alias в постоянную ссылку на старую версию.

Внутри Rust разделить три решения: куда устанавливать, требуется ли запрос restart, разрешено ли его выполнять. Elevated-запуск с `--here` может зарегистрировать пару и вернуть `RestartSkippedElevated`, не создавая Explorer. Это позволяет убрать необходимость в общем JS-fallback для этого штатного случая. Ошибка проверки токена должна давать явный отказ перезапуска.

Вместо `(PathBuf, bool, Vec<PathBuf>)` вернуть структуру с адресатом, фактом изменения регистрации, состоянием restart и leftovers. Состояния как минимум: `NotRequested`, `SkippedElevated`, `Restarted`, `Failed`. Для последнего сохранять фазу: старый процесс ещё работает либо уже завершён, новый не запущен. Если регистрация уже обновлена, результат должен об этом сообщать даже при ошибке restart.

Для `--to` не обещать безусловную транзакционность поверх `undo`, игнорирующего ошибки. [swap.rs](../../crates/win-make-ro/src/reinstall/swap.rs#L62), строки 62–67, сейчас теряет ошибки отката. Нужны сведения о восстановленных и оставшихся файлах. Подготовку обоих новых файлов лучше завершать до изменения действующих; очистку проводить по точному списку созданных backup, сохраняя возможность восстановления после частичного отказа.

При переходе между установщиками также стоит защитить uninstall: [uninstall_under](../../crates/ro-register/src/uninstall.rs#L14) сейчас безусловно удаляет общую регистрацию. Удаление старой Scoop-копии после активации npm не должно снимать регистрацию npm. Для пакетного hook нужна проверка принадлежности текущей регистрации удаляемой установке; общее ручное удаление можно оставить отдельным явным действием.

**Проверки, которые должны сопровождать исправление**

- Настоящий postinstall с подменённым `spawnSync`: полный argv, остановка после успеха, fallback и его сообщения, skip/local/non-Windows. Готовая локальная проверка уже демонстрирует этот способ.
- План Rust: первая регистрация; прежняя регистрация в том же каталоге; другой установщик; устаревшая регистрация; явный `--to`; elevated и ошибка чтения токена. Для `--here` файлы других установок должны остаться побитово прежними.
- Граница Explorer: отсутствие shell, ошибка OpenProcess, отказ PostMessage, timeout ожидания, ошибка запуска. При сбоях не выдавать `Restarted`; проверять закрытие handle.
- Файловая замена: сбой подготовки второй копии, ошибка отката, сохранение ручных backup, очистка только принадлежащих операции файлов.
- Отдельная проверка настоящего restart в выделенной Windows-сессии/VM: завершился старый PID, появился shell, используется новая сборка, elevated desktop не создаётся. Проверки логики через подмены не заменяют этот эксперимент.

Повторный запуск всех штатных проверок подтвердил числа отчёта: 89/89 Rust в debug и release, npm 8/8, PowerShell 17 кейсов, clippy, fmt и MSRV. Дополнительно выполнены 9 поведенческих JS-сценариев, Rust-проверка оркестрации с заменёнными границами ОС и настоящее обновление отдельного npm fixture с DLL, загруженной в процессе ревью. Пользовательский Explorer не перезапускался; реальные регистрационные ключи не менялись. Тестовый DLL handle освобождён.
