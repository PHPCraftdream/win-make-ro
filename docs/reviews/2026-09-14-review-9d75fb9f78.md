**P2. Позднее завершение Explorer после таймаута остаётся без последующего запуска.**

Место: [reinstall/explorer.rs](../../crates/win-make-ro/src/reinstall/explorer.rs#L63), строки 63–64; запрос завершения — строка 58, запуск новой оболочки — строки 67–69. Код не менялся в последних пяти файлах; замечание найдено при проверке всего проекта.

`PostMessageW` ставит запрос закрытия в очередь и возвращается, не дожидаясь его обработки. `WaitForSingleObject` с таймаутом 30 000 мс прекращает только ожидание; истечение времени не отменяет уже отправленное сообщение. Эти свойства описаны в [PostMessageW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-postmessagew) и [WaitForSingleObject](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject).

Сейчас после `WAIT_TIMEOUT` функция возвращает `Failed`, закрывает handle и не доходит до `start()`. Вызывающий код сообщает ошибку, после чего CLI завершается; фонового участника, ожидающего позднего выхода старого процесса, нет. Если занятый Explorer обработает запрос или закончит завершение уже после этого, утилита его не запустит. При используемом здесь штатном выходе оболочки, для которого код явно рассчитывает выполнять запуск самостоятельно, пользователь может остаться без Explorer после уже завершившейся команды.

Проверка выполнена без настоящего рабочего стола. Тело текущей `restart()` и обе её константы извлечены без изменения; определения токена, shell, Win32-вызовы и запуск заменены моделью с виртуальным временем. Контроль своевременного завершения вызывает запуск ровно один раз. При таймауте получено:

```text
at 30000 ms: helper returned failure, quit remains queued
late exit: old alive=false, new shell launches=0
```

Это подтверждение пути управления при указанной последовательности событий, а не результат закрытия настоящего Explorer. Реальный нативный случай позднего завершения отдельно не воспроизводился. Проблема следует из уже принятого асинхронного запроса и отсутствия наблюдения за его завершением после возврата функции.

Исправление: после отправки запроса сохранять ответственность за последующий запуск до фактического завершения старого процесса. Например, передавать ожидание отдельному помощнику до отправки сообщения и при таймауте основного CLI оставлять этому помощнику handle и обязанность однократного запуска. Истечение пользовательского ожидания должно означать «операция ещё выполняется», а не отмену уже принятого запроса. Простое увеличение 30-секундного лимита сохраняет ту же гонку. Нужен тест «таймаут → поздний выход → ровно один запуск» вместе с контролем отсутствия запуска до выхода старого процесса; окончательная проверка — в отдельной Windows-сессии/VM.

Дополнительно исправлена диагностика: CLI больше не утверждает, что старая оболочка обязательно продолжает работать при любом `Restart::Failed`.
